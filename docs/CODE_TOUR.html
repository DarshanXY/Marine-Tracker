Code Tour: where is the code for what we are showing?

Marine Plastic Tracker. This page connects everything you can see on screen to the exact lines of code behind it, and explains the logic in words you can say out loud to the panel.

  1. Open docs/CODE_TOUR.html in the browser. Click any file:line link and VS Code opens on that exact line (the first time, the browser asks "Open Visual Studio Code?" - tick always allow).
  2. Or open docs/CODE_TOUR.md in VS Code, press Ctrl+Shift+V, and Ctrl+click a link.

The three questions in 60 seconds

1. How do you detect plastic? Plastic floating on the sea reflects near-infrared light more than water does (water swallows it). We download a Sentinel-2 satellite image, compute the Floating Debris Index (FDI) for every pixel - "how much brighter than water is this pixel in near-infrared" - and keep the pixels above a threshold as candidates. FDI cannot tell plastic from seaweed, foam or wood, so a small neural network (MLP) looks at 11 spectral numbers per candidate and says Plastic / Algae / Sea-foam / Water with a confidence. Confident plastic pixels that sit close together are grouped by DBSCAN into hotspots; a second AI (Clay) double-checks them; and a drift model forecasts where each hotspot travels in 72 hours. Code: run_aoi() in main_pipeline.py - it is 80 lines and reads like the list above.

2. Where is the code of this UI? The screen in the screenshot is the Map Explorer page: MapExplorer.tsx:467. The seven "Live processing" cards are MapExplorer.tsx:1098. Every element is mapped to its code in section 3, and the full click-to-database chain is in section 2.

3. Why are the MADOS folders called 10, 20 and 60? It is the pixel size in metres. Sentinel-2 photographs different colours (bands) at different sharpness: 4 bands at 10 m, 6 bands at 20 m, and others at 60 m. The dataset stores each band in the folder for its own resolution. Full answer with our own numbers: section 5.

2. One click, end to end: "You draw a box - what runs?"

  1. You drag a rectangle. MapExplorer.tsx:50 listens to mousedown / mousemove / mouseup on the map and turns the drag into {north, south, east, west}. Boxes smaller than 0.01 degrees are ignored (MIN_DEG).
  2. The page reacts. setBbox(...) in MapExplorer changes state, which makes useAoiAnalysis fire automatically (React-Query). A new box always scans fresh (staleTime: 0); Go live repeats it every 30 seconds.
  3. The API call. api.analyzeAoi sends POST /api/pipeline/run with the box. The timeout is 130 s because a real satellite download is slow.
  4. Express checks the login. POST /run runs the authenticate middleware (valid JWT?), validates the box with parseBbox, and forwards it with callEngine (120 s timeout).
  5. FastAPI receives it. pipeline_run keeps a 20-second cache (so a double click does not download twice) and calls the orchestrator.
  6. The orchestrator runs seven stages. run_aoi - each stage records its own duration and a one-line detail; those become the cards on screen. Section 4 explains each stage.
  7. Back in Express, the result is saved. persistRun writes a SatelliteImage, all Detection rows, Hotspot rows, Trajectory rows, deduplicated Alert rows and one PipelineLog row per stage into PostgreSQL, then announces it on the WebSocket (publishLive). Saving is best-effort: if the database is down, the scan still returns.
  8. The browser draws the answer. Markers, the cards, the surface bar and the result panel all render from the one result object (see section 3).

What if something is down? Engine unreachable -> offlineAoiResult returns an honest "engine offline" result with no invented detections. Satellite download fails -> the engine falls back to a labelled synthetic scene (scene_for_bbox) and the UI says so (SurfaceReadout).

4. How plastic is detected: the seven stages

run_aoi in main_pipeline.py runs these in order. Every threshold below lives in one file: config.py.

Stage 1 - Scan scene (DOWNLOAD): get real pixels

  • What we ask for: five spectral bands B04, B06, B08, B8A, B11 plus the SCL land/cloud map, for the drawn box - BANDS and the request script _EVALSCRIPT.
  • From where: Copernicus Data Space "Sentinel Hub Process API", logged in with free OAuth credentials (get_token). One request returns all bands already aligned to one grid.
  • Cloud handling: we ask for a least-cloud composite - for every pixel, the clearest recent pass (max 50% scene cloud, last 45 days, widening to 180 days only if coverage is poor): ingest_max_cloud, _real_ingest.
  • Which pixels may become candidates: only SCL classes 6 (water) and 7 (unclassified) - ingest_keep_scl, keep_mask. Clouds, shadows, vegetation and bare soil are excluded.
  • Reliability grade: reliability_for calls a scan reliable / degraded / unusable from coverage and cloud/land share.

Stage 2 - FDI index (FDI): find "something floating"

The formula (Biermann et al., 2020), in floating_debris_index:

FDI = B08 - [ B06 + (B11 - B06) * (842 - 740) / (1610 - 740) * 10 ]

In words: draw a straight line between the red-edge band (740 nm) and the SWIR band (1610 nm). At the near-infrared wavelength (842 nm) that line tells you what plain water would reflect. FDI is how far the real NIR value sits above that line. Floating solids (plastic, wood, seaweed, foam) push NIR up; clean water does not.

  • Threshold: a pixel is a candidate if FDI > 0.02 (fdi_threshold). Applied to the whole image at once in extract_candidates.
  • Inland filter: candidates more than 3 km inland are dropped using country outlines from countries.geojson (Natural Earth): _COASTLINE, deep_inland.
  • Honest limit: FDI is a screen. It also lights up for seaweed, foam, ships, cloud edges and very turbid water. That is why stage 3 exists.

Stage 3 - Classify (CNN code, card says "MLP"): what is it?

  • Model: a small neural network, a multi-layer perceptron (MLP), exported as marinenet.onnx and run with ONNX Runtime (get_model). The shipped one is a 3-model ensemble (256-128-64-32 neurons each), trained on about 1.08 million labelled pixels - metrics.json.
  • Input - 11 numbers per pixel: the 5 bands, FDI, and 5 derived indices: NDVI (vegetation), PI (plastic index), MNDWI, red-edge NDVI, brightness - _features.
  • Output: one of four classes - Plastic, Algae, Sea_Foam, Water - and a confidence from softmax: predict and _detection.
  • Two confidence bars, do not mix them up: status = CONFIRMED at confidence >= 0.85 (AUTO_CONFIRM) is the analyst-facing label. high_confidence at >= 0.648 (plastic_high_conf) was calibrated on held-out data to about 90% precision and is the bar for creating hotspots.
  • Fallback: if the ONNX file is missing the engine uses hand-written rules and says heuristic on the card. REQUIRE_MODEL=1 makes a missing model a hard failure instead (_strict); the rules themselves are in classify.
  • Naming to be ready for: the card is labelled "Classify (MLP)" but its code is CNN. That is a historical stage name; the shipped model is a per-pixel MLP. A patch-based CNN exists but scored worse (macro-F1 0.55), so it is not shipped (the code comment).

Stage 4 - Cluster (DBSCAN): turn pixels into hotspots

  • Only high-confidence Plastic pixels are clustered - a crew is never sent because of a low-confidence guess: _make_hotspots.
  • DBSCAN (written from scratch, no library): pixels within 0.09 degrees (~10 km) of each other, at least 3 in a group, form a cluster - dbscan, parameters dbscan_eps_deg.
  • Severity by size: 10+ = HIGH, 5+ = MEDIUM, otherwise LOW - severity_for.

Stage 5 - Clay verify (CLAY): a second, independent opinion

  • Clay is a large pre-trained satellite "foundation model". enrich_hotspots cuts a small image around each hotspot, sends it to the GPU sidecar (clay_service.py), and combines Clay's view with the MLP's (confidence_fusion.py) into CONFIRMED or POSSIBLE.
  • Calibrated so CONFIRMED plastic is about 92% precise (70% recall) on held-out MARIDA+MADOS: fusion_thresholds.json.
  • Best-effort: if the sidecar is off, the card says Clay OFFLINE - MLP-only and the scan still works (_clay_stage).

Stage 6 - Drift: where does it go in 72 hours?

  • Physics: a floating parcel moves with the ocean current plus a small fraction of the wind ("windage", 1.5-3%). _velocity_deg adds them; integrate_members steps forward one hour at a time with Runge-Kutta 4.
  • Ensemble and cone: one track per windage value (0.015, 0.02, 0.025, 0.03) - DEFAULT_WINDAGE. The average is the path; the min/max envelope is the uncertainty cone.
  • Forcing data: real hourly currents and wind from Open-Meteo (fetch_forcing); if unreachable, a smooth synthetic field, labelled synthetic.
  • Landfall and ETA: the path is cut where it enters a land polygon (clamp_path) and the hour it happens becomes the coast ETA. Orchestrated in _drift_stage. Only the top 2 hotspots get a full track.
  • How good is it? We measured it against real NOAA drifter buoys (validate_drift_gdp.py, results in drift_gdp_results.json). For the 25 undrogued surface drifters (the closest stand-in for floating plastic; Indian Ocean, 2024-25), the median position error was about 12 km after 24 h, 22-26 km after 48 h and 29-33 km after 72 h. Assuming "it does not move" gives 23, 34 and 57 km, so the model roughly halves the error.
  • Two honest caveats to volunteer: (1) it is a hindcast (uses analysed currents and winds, not forecasts), so true forecast skill is lower; (2) the uncertainty cone is too narrow: it contains the buoy's real position only about 0% of the time at 24 h and 8% at 48-72 h, because it reflects wind-drag spread only, not the real error. Say "forecast with an uncertainty that is optimistic", never "prediction".

Stage 7 - Alerts

_alert_stage counts HIGH and MEDIUM hotspots. The backend then creates the real alert rows in persistRun: the same hotspot does not alert twice within 24 hours, and an alert is COAST_PROXIMITY if the coast ETA is 48 h or less.

5. Why the folders are named 10, 20 and 60

Short answer: the number is the ground pixel size in metres of the images inside that folder.

Sentinel-2's camera records 13 colours ("bands"), but not all with the same sharpness. That is a sensor design trade-off (data volume and light available per band):

Folder Pixel size Bands inside (MADOS, wavelength in nm) Sentinel-2 names
10 10 m 492, 559, 665, 833 B02 blue, B03 green, B04 red, B08 NIR
20 20 m 704, 739, 780, 864, 1610, 2186 B05, B06, B07 red-edge, B8A, B11, B12 SWIR
60 60 m 442 B01 coastal aerosol

(Checked on data/MADOS/Scene_0: 4 + 6 + 1 = 11 bands. The 10 m folder also holds the label masks cl, conf, rep and the RGB previews, because the annotators drew on the 10 m grid.)

Every crop covers the same 2.4 km x 2.4 km, so the images are different sizes: 240 x 240 pixels at 10 m, 120 x 120 at 20 m, 40 x 40 at 60 m.

Why it matters for us. Our detector needs five bands: B04 and B08 (10 m folder) and B06, B8A, B11 (20 m folder). To give every pixel all five values, the training loader stretches the coarser images onto the 10 m grid - factor = folder // 10, so 20 m is repeated 2x2 and 60 m 6x6 (nearest neighbour): _crop_bands in mados.py. The general helper is band_resampler.py, whose docstring says exactly this.

In the live app we do not touch these folders. Sentinel Hub delivers all requested bands already resampled to one grid (_grid_for). One honest consequence: FDI uses B06 and B11 (20 m) with B08 (10 m), so its true detail is closer to 20 m; we count one candidate pixel as a single 10 m cell (0.0001 km2).

8. The backend, in order of how a request travels

  • Startup and safety: helmet (secure headers), CORS, rate limiting, JSON parser, then all routes under /api (routes/index.ts).
  • Login and roles: JWT access token (15 minutes) plus a refresh token (7 days) - env.ts. Three roles: FIELD (1), COASTGUARD (2), ADMIN (3) - ROLE_LEVEL. requireMinLevel enforces them on the server, so hiding a button is never the only protection. Passwords are checked with bcrypt in validateCredentials, tokens are created in issueTokens, and two-factor (TOTP) is set up in setupTotp.
  • Engine proxy: proxy forwards /api/engine/* (forecast, change detection, similarity, model evaluation) to the Python engine.
  • Saving results: persistRun (section 2, step 7). The database tables are defined in schema.prisma (also Hotspot, Alert, Trajectory, Region, User, Operation, SavedArea, AreaForecast). These live in PostgreSQL; python database\mysql\sync_app.py copies them into the MySQL database mpt_app for reporting (section 1).
  • Job queue and schedule: startWorker (BullMQ on Redis) runs scans in the background; /scheduled-run lets a scheduler trigger scans of every monitored region. Everything falls back to a direct call if Redis is down.
  • Live updates: attachLiveSocket pushes events to the browser over a WebSocket; the browser side is useLiveFeed.

10. Questions the panel is likely to ask

Why FDI and not just a photo? Plastic is often smaller than a pixel and grey/brown like the sea; in visible light it is invisible, but in near-infrared floating solids stand out. floating_debris_index

11. Weak points, and how to say them honestly

Panels respect a team that knows its limits. These are all measured, not guessed.

  • Independent test on real deployed plastic (PLP 2021). A ~28 m HDPE mesh was anchored at a known spot and imaged on 21 Sentinel-2 passes (zero overlap with training data). At the surveyed position, in a 3x3-pixel window: the model called something Plastic on 33% of passes; the FDI screen alone fired on 76%; a wood control raft was also called Plastic on 80% of passes; but false alarms on all the other water were 0% (median). Read it as: few false alarms, but a small target is often missed, and wood cannot be told apart from plastic in these bands. Why: the target is only 2-3 pixels wide, so each pixel is part plastic, part water; and wood and plastic reflect similarly. Definitions: validate_plp.py; numbers: plp_validation.json. The Clay second opinion is our attempt to improve this.
  • Plastic is very rare in the training data (about 0.5%), so plastic scores are lower than water scores. This is why we report macro-F1 and a high-confidence tier instead of raw accuracy.
  • A satellite sees aggregated floating matter, not single bottles. "Plastic" here means floating debris that spectrally behaves like plastic.
  • Revisit time is about 5 days, and clouds leave gaps - the 44% observed figure on screen is that limitation made visible.
  • New seas may behave differently. Only two scenes from seas outside the training data (RFO Durban and Marmara) were used as a check; that is thin evidence, so do not claim it works everywhere.
  • Drift error is real and the cone under-states it (about 12 km at 24 h, ~30 km at 72 h; cone holds the truth only 0-8% of the time; hindcast, not forecast) - see section 4, stage 6.

12. Before you present: a 6-point checklist

  1. Start everything with start-all.cmd and wait for all windows (engine :8000, Clay :8010, backend :3001, frontend :5173). Without the Clay window the Clay verify card says OFFLINE.
  2. Map Explorer -> Advanced tools -> Min confidence must be 0%. If it is high, the Classify card can read "0 plastic of 0 classified" even though the FDI card found hundreds of candidates.
  3. If you see the orange "RESTORED - NOT RE-SCANNED" badge, press Rescan so the cards show a fresh run (a real scan takes about a minute; the download is the slow part).
  4. Draw over open sea for the demo. A box on land or cloud is supposed to show the amber warning and no markers. 0 plastic on a clean sea is a correct result, not a fault - say so.
  5. Know the demo plastic. On the Areas page, if a saved scan has no plastic, the backend adds a synthetic cluster so the drift forecast has something to release (withDemoPlastic, switch DEMO_PLASTIC in env.ts). The page labels it with an amber "Demo plastic" banner (Areas.tsx). Tell the panel first; set DEMO_PLASTIC=false in .env and restart the backend if you would rather not show it.
  6. Test one link now. Open docs/CODE_TOUR.html, click a file:line link, allow the "Open Visual Studio Code?" prompt. Then run python docs\code-tour\build_code_tour.py --check to confirm every link still lands after any last-minute edits (if you changed code, rebuild with C:\Anaconda\python.exe docs\code-tour\build_code_tour.py).
