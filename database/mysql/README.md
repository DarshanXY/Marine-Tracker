# MySQL dataset browser

Two MySQL databases that make every dataset in the project visible as ordinary tables
(and chart-ready views) in **MySQL Workbench** or any SQL / BI tool.

| Database | What it holds | Built by |
|---|---|---|
| `mpt_datasets` | MARIDA, MADOS, RefinedFloatingObjects, Plastic Litter Project, country polygons, the 2.1 M labelled training pixels, model metrics | `load_datasets.py` |
| `mpt_app` | A snapshot of the live app tables (detections, hotspots, alerts, regions, pipeline logs, ...) copied from PostgreSQL | `sync_app.py` |

The app itself still runs on PostgreSQL. These MySQL databases are a **read-only copy for
browsing, reporting and presentations** - nothing in the backend reads from them.

## One-time setup

1. In MySQL Workbench, connect as **root** and run
   `database/mysql/00_setup_user.local.sql` (creates the two databases and a low-privilege
   `mpt_loader` account limited to those two databases). The file is git-ignored because it
   contains a generated password; the same password is in the repo-root `.env` (`MYSQL_*`).
2. Load the data (Python 3.14 with `numpy`, `pyshp`, `tifffile`, `mysql-connector-python`):

```powershell
cd database\mysql
pip install -r requirements.txt
python load_datasets.py      # ~5-10 min: rebuilds mpt_datasets from scratch
python sync_app.py           # ~1 min:   rebuilds mpt_app from PostgreSQL
python build_dashboard.py    # writes dashboard.html (charts) from the loaded tables
```

Both loaders are full rebuilds, so re-running them is always safe. `load_datasets.py --dry-run`
parses everything without touching a database; `--skip pixels` skips the big pixel table.

## Looking at it

In Workbench: **Schemas** panel -> `mpt_datasets` -> **Tables** / **Views**. Right-click a table ->
*Select Rows*. For an entity-relationship diagram: **Database -> Reverse Engineer** and pick
`mpt_datasets`.

Start with these views (each is one chart or one summary table):

| View | Shows |
|---|---|
| `v_dataset_overview` | every dataset, its size on disk, and how many rows landed here |
| `v_table_inventory` | every table with row count, size and a plain-English description |
| `v_class_balance` | how imbalanced the 4 classes are (Water dominates) |
| `v_pixels_by_dataset_class` | pixels per dataset x split x class |
| `v_spectral_signature` | mean reflectance / FDI / NDVI per class - why the classes are separable |
| `v_marida_class_distribution`, `v_mados_class_distribution` | the native 15-class distributions |
| `v_rfo_site_summary`, `v_plp_targets_by_material` | the two external validation sets |
| `v_model_comparison`, `v_model_class_scores`, `v_confusion_matrix` | held-out model results |
| `v_load_problems` | anything that did not match an independent count (should be empty) |

`mpt_app` has matching `v_detections_by_class`, `v_detections_per_day`, `v_hotspots_by_severity`,
`v_alerts_summary`, `v_pipeline_stage_performance`, ...

MySQL Workbench has no chart widget. For charts, open `dashboard.html` (generated by
`build_dashboard.py`, no server needed) or connect Power BI / Excel / Metabase / Grafana to the
views above.

## What is - and is not - in MySQL

**Stored as tables:** everything tabular - the labelled training pixels, patch / crop / scene
catalogues with per-class pixel counts, official train / val / test splits, annotation polygons
(reprojected UTM -> lon/lat), plastic-target positions, labelled points, country polygons, model
metrics, and a verbatim copy of each model / validation summary JSON (`json_documents`).

**Left on disk:** the raw GeoTIFF imagery (~16 GB: MARIDA 4.5 GB, MADOS 5.6 GB, RFO 12 GB). Raster
pixels do not belong in a relational table; the tables keep each image's id and footprint so a row
points straight to its file under `data/`.

**Not copied from PostgreSQL (credentials):** the `refresh_tokens` and `api_keys` tables and any
column named like `password_hash` / `totp_secret`. `sync_app.py` prints exactly what it left out.

**Empty on purpose:** `data/ocean_data`, `data/wind_data` and `data/seed` contain no files - drift
forcing (currents / wind) is fetched live at run time, so there is no local dataset to convert.

**Not georeferenced:** the MADOS crops (label masks and band files alike) carry a CRS code but no
position, so the MADOS `center_lon / center_lat / min_* / max_*` columns are NULL. MARIDA, RFO and PLP
do have positions and are fully located.

## Trust but verify

Every load step cross-checks its row count against an independent source and writes the result to
`load_audit` (for example: mapped-class pixels counted from the MARIDA / MADOS masks must equal the
row counts of the training `.npz` files, and the official multi-hot MARIDA labels must equal the
classes actually present in each mask). `SELECT * FROM mpt_datasets.v_load_problems;` lists any miss.

## Files

| File | Purpose |
|---|---|
| `00_setup_user.local.sql` | one-time root script (git-ignored) |
| `schema_datasets.sql`, `views_datasets.sql` | `mpt_datasets` tables and views |
| `views_app.sql` | `mpt_app` views (tables are generated from PostgreSQL) |
| `load_datasets.py`, `sync_app.py`, `build_dashboard.py` | the loaders and the chart page |
| `_common.py`, `_geo.py` | helpers (connection, UTM -> lon/lat without pyproj) |

`001_create_tables.sql` ... `005_create_indexes.sql` in this folder are empty one-line placeholders
from the original scaffold and are not used.
